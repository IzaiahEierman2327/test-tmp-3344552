# Project Euler Workbench v0.4.0

v0.4.0 is a hardening and reliability release built on the v0.3 Workbench architecture. It keeps the existing Project Euler + JupyterLab workflow while tightening privileged boundaries, bounding failure cases, preserving Project Euler login sessions correctly, and making the JavaScript desktop build reproducible.

## Highlights

- Project Euler login state now survives Workbench restarts even when authentication is represented by session cookies. Only `projecteuler.net` session cookies are mirrored, the snapshot is encrypted with Electron `safeStorage`, and cookies are restored before the first left-pane navigation.
- Explicit Project Euler logout wins over any stale asynchronous cookie read and removes the encrypted session snapshot, so an old login is not revived on the next launch.
- Managed package specifications reject pip option injection, and Workbench terminates pip option parsing before the user-supplied package requirement.
- Managed `pip list` and `pip install` operations now have bounded lifetimes instead of being able to hang the Tools workflow indefinitely.
- Privileged local BrowserWindows are prevented from navigating to remote content while retaining Workbench preload privileges.
- Privileged `tools:*` IPC calls are accepted only from the active Tools window, and the Tools renderer uses a restrictive Content Security Policy.
- OpenAI-compatible AI requests have a bounded timeout instead of waiting forever for a stalled endpoint.
- The Electron/build toolchain now has a committed npm lockfile. CI and release builds install JavaScript dependencies with `npm ci`.

## Python/runtime policy

v0.4.x remains on the **CPython 3.13 series**. Builds continue to prefer the latest stable supported 3.13 patch release available from the existing `python-build-standalone` source and the highest stable compatible Python libraries.

The npm lockfile applies only to the JavaScript/Electron build toolchain. The Python environment is intentionally not converted into a fully exact-pinned snapshot merely for reproducibility. A future move to another Python minor series, such as 3.14, requires a separate compatibility decision.

## Distribution

v0.4.0 publishes exactly these x64 assets:

- Windows NSIS installer: `euler-workbench-0.4.0-win-x64-setup.exe`
- Windows portable ZIP: `euler-workbench-0.4.0-win-x64.zip`
- Linux portable tarball: `euler-workbench-0.4.0-linux-x64.tar.gz`

macOS is not part of the active release matrix.

## Upgrading from v0.3.0

### Installed Windows edition

Close Project Euler Workbench, then run the v0.4.0 installer normally. The stable application ID is unchanged. User notebooks, Workbench settings, managed Python packages, Electron profile/session data, and other persistent state remain outside replaceable application files. The installer continues to keep application data on uninstall.

### Portable Windows/Linux edition

Close Project Euler Workbench and replace/extract the new program files while preserving the existing neighboring `data/` directory. Release archives intentionally contain no `data/` directory, so the new archive does not overwrite portable user data.

As with earlier portable versions, move or back up the complete portable folder only while the application is closed.

## Security and behavior notes

- The Project Euler page is still never scraped for AI generation.
- `submit(value)` still only fills the Project Euler answer field; Workbench never clicks the site's submit control automatically.
- User package installs still go only to the persistent managed `python-packages/` layer and do not modify the bundled base runtime.
- If Electron secure storage is unavailable on a system, Workbench does not fall back to plaintext session-cookie persistence; the user may need to sign in again after restart.
- Existing persistent Chromium cookies and DOM storage remain owned by Chromium; Workbench only mirrors Project Euler session cookies that Chromium would otherwise discard between application sessions.

## Validation

The release pipeline requires:

- locked JavaScript dependency installation with `npm ci`;
- unit tests;
- self-contained CPython runtime preparation and isolation verification;
- real Jupyter integration smoke testing;
- desktop package construction on Windows and Linux;
- packaged-runtime verification;
- portable-layout verification;
- exact final validation of the three expected release assets before publication.
